# 00 · SDD 流程说明

> 本文档定义本项目的文档体系、编号规则、变更管理与开发流程。它是后续所有文档与合作约定的**元规则**。

## 1. 目标

用一套**可评审、可追溯、可验收**的规范文档驱动系统从零到一，避免"先写代码再补文档"的返工，确保每一行实现都有对应规格支撑。

## 2. 文档体系与层级

规范文档按 `01 → 07` 顺序递进，后者依赖前者，形成一条**单向依赖链**：

```
01 需求规范 ──> 02 领域数据模型 ──> 03 架构设计 ──> 04 API 契约
     │                                                    │
     └────────────> 05 前端界面/路由 <──────<──────────────┘
                                   │
                                   └──> 06 任务分解 ──> 07 测试与验收
```

- **01 需求**：定义"做什么"（产品视角）。
- **02 数据模型**：定义"存什么"（数据视角）。
- **03 架构**：定义"怎么搭"（技术视角）。
- **04 接口**：定义"前后端怎么通信"（契约视角）。
- **05 界面**：定义"用户看到什么"（交互视角）。
- **06 任务**：定义"按什么顺序做"（执行视角）。
- **07 测试**：定义"怎么算做对了"（验收视角）。

## 3. 编号与引用规则

- 每个需求、实体、接口、页面、任务都有全局唯一 ID，便于追溯。
- 编号前缀约定：

| 前缀 | 含义 | 示例 |
| --- | --- | --- |
| RQ-  | 需求 | `RQ-NOT-01` |
| ENT- | 数据实体 | `ENT-NOTE` |
| API- | 接口 | `API-NOTE-LIST` |
| PG-  | 页面/路由 | `PG-NOTES` |
| T-   | 任务 | `T-1.1` |

- 实现时在代码注释或提交信息中标注对应编号，如 `// 对应 RQ-NOT-01`。
- 测试用例引用其验证的需求/接口编号，保证**需求 ↔ 代码 ↔ 测试**三者可互相追溯。

## 4. 版本与变更管理

- 每份文档首部含 `版本`、`更新日期`、`作者`、`变更记录`。
- 发生需求变更时：先改对应文档并升版本 → 更新受影响的衍生文档 → 最后才改代码。
- 重大变更（涉及数据模型或接口契约）需在文档中标注 `⚠️ BREAKING`。
- 文档采用 **Markdown**，存储于 `docs/`，以 Git 管理版本（如后续接入）。

## 5. 开发流程（每轮迭代）

```
1. 确定本轮目标（对应文档 06 的某个里程碑）
2. 核对范围与规格（01/02/03/04/05）
3. 后端：模型 -> Schema -> 路由 -> Service + pytest
4. 前端：API 客户端 -> Pinia 存储 -> 视图组件 + 路由
5. 联调（Vite dev proxy -> FastAPI）
6. 跑测试/构建 -> 核对验收标准（07）
7. 更新任务状态，标记完成
```

## 6. 角色与约定

- **单开发者 + AI 协作**：本系统由学生本人学习使用，同时作为编程实践。
- **约定**：宁简勿繁；凡有多个合理方案，择其最简单且可扩展者。
- **定义"完成"（Definition of Done）**：功能可用 + 配套测试通过 + 对应验收标准满足 + 文档编号已标注。

## 7. 明确的设计原则

1. **单用户优先**：本机为主，但后端需支持被其它设备经网络访问（见文档 03）。
2. **LaTeX 公式一等公民**：所有涉及数学文本的输入输出都用 KaTeX 渲染。
3. **数据自持**：SQLite 单文件，便于备份与拷贝迁移。
4. **前后端松耦合**：前端只通过 REST API 通信，不直接操作数据库。
